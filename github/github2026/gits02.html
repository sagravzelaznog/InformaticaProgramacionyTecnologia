Sesión 2: El Área de Preparación y Commits

← Volver al Temario Principal

Antes de registrar tus cambios de forma permanente, necesitas agregarlos al área de preparación.

Añadir todos los cambios (git add -A)

Para mover todos los archivos modificados, nuevos y eliminados al área de preparación en cualquier versión de Git, se recomienda utilizar git add -A o su equivalente git add --all [1].

Modo interactivo y fragmentos (git add -p)

En lugar de preparar archivos enteros, puedes revisar los "hunks" (fragmentos) de trabajo de forma interactiva utilizando el flag -p o --patch [2].

Comentario: git add -p es útil cuando queremos ser selectivos con lo que incluimos en cada commit, permitiendo preparar cambios línea por línea o bloque por bloque.

git add -p

Esto abrirá un prompt interactivo que te permitirá mirar las diferencias en el código y decidir si deseas incluirlas en el próximo commit [2]. Algunas de las opciones interactivas incluyen:

  • y: Sí, preparar este fragmento.
  • n: No preparar este fragmento.
  • s: Dividir el fragmento en pedazos más pequeños [2].
  • e: Editar manualmente el fragmento en un editor de texto [2].

Un commit representa un "guardado" o "instantánea" de todo tu proyecto [3].

Banderas de comando rápido (-m y -a)

Comentario: las banderas -m y -a aceleran el flujo de trabajo para cambios simples, pero no descuides la calidad del mensaje de commit.

  • El flag -m: Evita que Git abra el editor de texto predeterminado permitiéndote pasar el mensaje de confirmación directamente desde la línea de comandos [4-6]:
    git commit -m "Mensaje de commit aquí"
  • El flag -a: Si sólo has modificado o eliminado archivos existentes (y no has creado nuevos), puedes combinar la fase de staging y commit pasando la opción -a (o --all) [6]. Se puede fusionar con el mensaje así [7]:
    git commit -am "tu mensaje de commit aquí"

Convenciones para buenos mensajes de commit

Es importante que cualquier persona que navegue por el historial entienda fácilmente de qué trató cada commit [8]. Un buen mensaje usualmente incluye un número de tarea/incidencia, una descripción concisa de lo que se hizo, el por qué y, en ocasiones, cómo se hizo [8].

Comentario: invierte tiempo en escribir buenos mensajes de commit; son la documentación viva de tu proyecto. Un historial limpio facilita los revert, blame y búsquedas posteriores.

El modo imperativo: Una buena regla para probar si el mensaje está escrito en el modo correcto es rellenar la siguiente oración [9]: "Si aplico este commit, esto ___ a mi repositorio." (Ej: "Añadirá la minificación de JS/CSS") [9].

Las reglas para un gran mensaje de commit [10]:
  1. Separar la línea de asunto del cuerpo con una línea en blanco.
  2. Limitar el asunto a 50 caracteres.
  3. Poner la primera letra del asunto en mayúscula.
  4. No terminar la línea de asunto con un punto.
  5. Usar modo imperativo en el asunto.
  6. Envolver (wrap) las líneas del cuerpo a 72 caracteres.
  7. Usar el cuerpo para explicar "qué" y "por qué" en lugar del "cómo".

Si tu último commit aún no ha sido publicado (es decir, no ha sido enviado o "pushed" al servidor remoto), puedes modificarlo fácilmente de manera segura [10].

Corregir mensajes o archivos

Si olvidaste incluir algunos archivos o te equivocaste en el mensaje, simplemente prepara los cambios en tu directorio de trabajo (git add) y ejecuta [11]:

Comentario: --amend es tu amigo para correcciones locales, pero recuerda: nunca lo uses en commits que ya publicaste en remoto y otros colaboradores podrían estar usando.

git commit --amend

Esto tomará los cambios actualmente en el área de staging y los aplicará encima del último commit, reemplazándolo por completo sin crear uno nuevo [5, 11]. Se abrirá tu editor por defecto permitiéndote cambiar el mensaje previo [11].

Opciones para --amend

  • Para especificar un nuevo mensaje de forma directa [11]:
    git commit --amend -m "Nuevo mensaje de commit"
  • Para agregar los archivos olvidados sin cambiar el mensaje del commit original [11, 12]:
    git commit --amend --no-edit

Cuidado: Debido a que --amend reemplaza el commit por completo removiendo el original del historial, no debes utilizarlo en commits que ya compartiste en un repositorio público con otros colaboradores [5].
