Sesión 10: Flujos de Trabajo en Git (Workflows)

Con este modelo de flujo de trabajo fundamental, una sola rama master contiene todo el desarrollo activo [1]. Es la aproximación más similar a sistemas antiguos como Subversion o CVS.

Cómo funciona

Todos los desarrolladores tienen acceso al repositorio central y pueden hacer commits directamente sobre la rama master [1]. Debido a esto, los contribuidores deben asegurarse de hacer "pull" de los últimos cambios frecuentemente antes de continuar su desarrollo, ya que la rama cambiará muy rápido [1].

Desventajas: Aunque Git es capaz de trabajar de esta manera, requiere preceder casi cada push con una fusión (merge). Resolver conflictos constantemente puede terminar consumiendo mucho tiempo valioso del equipo [1].

Propuesto originalmente por Vincent Driessen, Gitflow es un flujo de trabajo que utiliza varias ramas predefinidas con propósitos específicos para gestionar ciclos de desarrollo formales [2].

Estructura de ramas en Gitflow

  • master: Siempre contiene el código de producción más reciente. No se permite código experimental aquí [3].
  • develop: Contiene todo el desarrollo activo más reciente. El código aquí se trabaja y se prepara para la siguiente liberación [3].
  • feature: Ramas reservadas para desarrollar características grandes. Se separan del código principal para crear funcionalidades independientes y, al terminar, se fusionan en develop [3].
  • release: Se usan para liberar nuevos desarrollos pasando de develop a master. Aquí se realizan cambios de último minuto (como incrementar la versión) [3].
  • hotfix: Ramas para correcciones de errores urgentes que no pueden esperar al próximo ciclo de lanzamiento. Nacen directamente de master y al finalizar deben fusionarse de vuelta en master y también en develop [3].

Estos flujos de trabajo se centran en el desarrollo ágil mediante aislamiento y revisiones colaborativas de código.

Feature Branch Workflow

La idea central es que todo el desarrollo de nuevas características debe llevarse a cabo en ramas dedicadas en lugar de en la rama master [4]. Esta encapsulación permite que varios desarrolladores trabajen sin perturbar el código principal, garantizando que master nunca contenga código roto (ideal para entornos de integración continua) [4].

Pull Requests y GitHub Flow

Encapsular características hace posible el uso de Pull Requests, una herramienta para iniciar discusiones sobre una rama y revisar el código antes de que se integre al proyecto oficial [5]. El flujo de GitHub (GitHub Flow) dictamina lo siguiente [6]:

  • Cualquier cosa en la rama master debe ser desplegable (deployable) [6].
  • Trabajas en una rama descriptiva que nace de master [6].
  • Haces commits locales y subes la rama al servidor regularmente [6].
  • Abres un Pull Request para obtener comentarios y retroalimentación [6].
  • Una vez que alguien más revisa y aprueba el código, lo fusionas (merge) en master y despliegas inmediatamente [6].

Este flujo es fundamentalmente diferente a los demás y es ideal para proyectos de código abierto (Open Source) [7].

Mecánica del Forking

En lugar de que todos los desarrolladores tengan acceso de escritura a un repositorio centralizado, cada desarrollador clona (hace un fork) su propio repositorio a partir del repositorio principal [7].

La ventaja de esto es que cada desarrollador puede subir (push) sus cambios a su propio repositorio privado y público, sin tocar el repositorio compartido. Finalmente, un "mantenedor" del proyecto original se encarga de revisar los Pull Requests y puede integrar los cambios de los repositorios clonados al repositorio original solo cuando lo considere apropiado [7].
